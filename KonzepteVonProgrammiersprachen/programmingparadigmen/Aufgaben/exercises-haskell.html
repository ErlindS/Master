  • Accumulator recursion

Recall the definition of summing up a list of elements

sumNums xs 
  | null xs = 0
  | otherwise = head xs + sumNums (tail xs)

Consider the following alternative definition.

sumNums' = sumNumsAcc 0
sumNumsAcc acc xs  
  | null xs = acc
  | otherwise = sumNumsAcc (acc + head xs) (tail xs)

The main difference is that we accumulate the sum of elements via some additional argument.

Implement a accumulator-recursive definition of rev (the function for reversing a list of elements)

Note: Accumulator recursive functions are in tail recursion form. Compard to general recursive functions, a function in tail recursion form doesn't require any additional stack space because the function can be straightforwardly turned into a while-loop by the Haskell compiler. In principle, all functions can be turned into tail recursion form.

Expression evaluator (data types)

Your task is to implement an evaluator (think interpreter) for a simple expression language. Check ilias for a code template (see Exp.hs).

The language of expressions is defined by the following data type.

data Value = N Int | B Bool deriving Show

data Exp = Val Value | Plus Exp Exp | Minus Exp Exp | Times Exp Exp
         | Div Exp Exp | Equal Exp Exp | Gt Exp Exp 
         | And Exp Exp | Not Exp deriving Show

Here's a representation of "1 + (3 * 5)".

e1 :: Exp
e1 = Plus (Val (N 1)) 
          (Times (Val (N 3)) (Val (N 5)))

The actual evaluator takes an expression and yields a value. Well, we must be careful to catch "illegal" expressions. Therefore, the type of the evaluator function evalExp is as follows.

data Res a = Res a | Err String
evalExp :: Exp -> Res Value

What kind of illegal expressions do we need to catch?

  • Division by zero
  • Type incompatability

The above Exp data type describes the untyped syntax of expression. For example, we can define the following meaningless expressions

e1 :: Exp
e1 = Plus (Val (B True)) (Val (N 1))

e2 :: Exp
e2 :: Equal (Val (B True)) (Val (N 1))

The above expressions are meaningless because we can't provide for a well-defined semantics to add/compare integers and booleans. Of course, we could apply the C rule and via booleans like integers but that's not what we want here.

The consequence is that our evaluator may get "stuck". Of course, we wish to provide some meaningful feedback to the user for such cases. As an example, consider the definition of Plus

evalExp :: Exp -> Res Value
evalExp (Val v) = Res v
evalExp (Plus e1 e2) = 
   case (evalExp e1, evalExp e2) of
    (Res (N i1), Res (N i2)) -> Res (N (i1 + i2))
    x                        -> errorHandler x "plus: incompatible type"

The errorhandler function provides for a uniform handling of the erroneous cases.

errorHandler x msg = 
   case x of
    (Err s1, Err s2)         -> Err (unlines [s1, s2])  -- propagate failure
    (Err s1, _)              -> Err s1
    (_, Err s2)              -> Err s2
    _                        -> Err msg                 -- new failure

For example, if both results have failed, we propagate both failure strings. If one of the results have failed we propagate them. For a new falure, we use a customized failure message.

Lambda calculus interpreter in Haskell (First-order syntax)

We introduce a data type to represent lambda terms.

data Term = Var Int 
          | Fun Int Term 
          | App Term Term

For example, is represented in Haskell as follows.

Fun 1 (Fun 2 (Var 2)

We use here numbers (integers) to represent variables. Recall that we assume that lambda-bindings always introduce fresh, distinct variables. Hence, the first argument of Fun will be a distinct number.

We could use our Term language to describe the result of evaluation but instead will use a more specialized data type.

data Val = VInt Int | VFun (Val->Val)

-reduction will be performed exhaustively and therefore function application is omitted.

Here's the definition of our lambda-calculus evaluator.

type Env = Int->Val

eval :: Env -> Term -> Val
eval env (Var x) = env x
eval env (Fun x t) = VFun (\y-> let env' z = if z==x then y else env z
                                in eval env' t)
eval env (App t1 t2) = let VFun f = eval env t1
                       in f (eval env t2)

Env represents the substitution binding. Notice how the Fun constructor is turned into Haskell function.

The immediate question is why not directly use Haskell functions as our term language? This is what we will consider next. For the record, the above style is referred to as "first-order abstract syntax encoding" (FOAS) and the upcoming style as "higher-order abstract syntax encoding" (HOAS).

Abstract because don't consider here a concrete source language but some abstraction where we ignore the common syntactic sugar present in a programming language. First-oder means that we use plain values to represent terms, e.g. numbers to represent variables etc. Higher-order means that we use Haskell variables to represent lambda term variables, Haskell functions to represent lambda functions etc.

Lambda calculus interpreter in Haskell (Higher-order syntax)

Here's the representation in Haskell

data Term = Zero | Succ Term | Plus Term Term 
         | Fun (Term->Term) 
         | App Term Term

The evaluation takes now a Term value and produces another Term value.

eval :: Term -> Term
eval Zero = Zero
eval (Succ e) = Succ (eval e)
eval (Plus Zero e) = eval e
eval (Plus (Succ e1) e2) = Succ (eval (Plus e1 e2))
eval (Fun f) = Fun f 
eval (App f e) = case (eval f) of 
                  Fun f' -> eval (f' (eval e))

Some examples

one = Succ Zero
two = Succ one
e1 = Fun (\ x -> Plus x two)
e2 = App e1 two
*Main> eval e1
Functions!
*Main> eval e2
4

We can only show concrete values. For function values we simply print the String "Functions!"

As we have seen earlier, evaluation may get stuck in case of an illegal term.

e3 = App one e1        -- 1 (\x->x+2)

*Main> eval e3
*** Exception: Lambda.hs:(30,18)-(31,46): Non-exhaustive patterns in case

In the above expression we find one in function position. Attempting to perform function application yields an exception (because of the partial function definition in App).

Well-typed interpreters

Our goal is to statically rule our illegal terms. We use a GADT which encodes the typing rules of the simply-typed lambda calculus.

data Term a where 
  Inj :: a -> Term a
  Zero :: Term Int
  Succ :: Term Int -> Term Int
  Plus :: Term Int -> Term Int -> Term Int
  Fun :: (Term a -> Term b) -> Term (a->b)
  App :: Term (a->b) -> Term a -> Term b

The evaluator functions takes a well-typed term of type Term a and yields a value of type a. The important point to note is that there is no longer a need to "wrap up" values inside some constructors. The Inj constructor is necessary for injecting values into the term language. See the function definition for Fun.

eval :: Term a -> a
eval (Inj x)             = x
eval Zero                = 0
eval (Succ e)            = 1 + eval e
eval (Plus (Inj x) e)    = x + eval e 
eval (Plus Zero e)       = eval e
eval (Plus (Succ e1) e2) = 1 + eval (Plus e1 e2)
eval (Fun f)             = \x -> eval (f (Inj x)) 
eval (App f e)           = (eval f) (eval e)

Our earlier examples from before

one = Succ Zero
two = Succ one
e1 = Fun (\ x -> Plus x two)
e2 = App e1 two

*Main> eval two       
2
*Main> eval e2        
4

The illegal expression

e3 = App one e1        -- 1 (\x->x+2)

won't type check any longer.

We obtain the error message

    Expected type: Term (a0 -> b0)
      Actual type: Term Int
    In the first argument of `App', namely `one'
    In the expression: App one e1

Lazy evaluation and space leaks

Consider the following program which attempts to sum up all numbers from 1 to 10^6

sumAcc acc [] = acc
sumAcc acc (x:xs) = sumAcc (acc+x) xs
mySum = sumAcc 1
main = do print $ mySum $ take (10^6) $ [1..]

Compile and execute the above program (we require here the compiler ghc instead of the interpreter ghci)

> ghc HigherOrderLazy.hs
[1 of 1] Compiling Main             ( HigherOrderLazy.hs, HigherOrderLazy.o )
Linking HigherOrderLazy ...
> ./HigherOrderLazy 
Stack space overflow: current size 8388608 bytes.
Use `+RTS -Ksize -RTS' to increase it.

We have hit a space leak. The expression acc+x won't be evaluated and therefore we accumulate a large chain of unevaluated expressions. Once we attempt to print the result we force evaluation which then results in a stack overflow.

The common fix is to force evaluation of acc + x. There are several methods. We use here the seq combinator.

sumAcc2 acc [] = acc
sumAcc2 acc (x:xs) = (acc+x) `seq` sumAcc2 (acc+x) xs
mySum2 = sumAcc2 1
main = do print $ mySum2 $ take (10^6) $ [1..]

Compile and execute the above and you'll see that the program will run without problems.

Parser Monad

import Control.Monad

------------------------------------------------------
-- The Parser Monad

newtype Parser a = Parser (String -> [(a,String)])

run :: Parser t -> String -> [(t, String)]
run (Parser p) s = p s

parse (Parser p) = p

instance Monad Parser where
  return a = Parser (\cs -> [(a,cs)])
  p >>= f  = Parser (\cs -> concat [parse (f a) cs' | (a,cs') <- parse p cs])


instance MonadPlus Parser where
  mzero = Parser (\cs ->[])
  p `mplus` q = Parser (\cs -> parse p cs ++ parse q cs)

------------------------
-- Some combinators 


-- deterministic (first) choice
(+++) :: Parser a -> Parser a -> Parser a
(+++) p q = Parser ( \cs -> case parse (p `mplus` q) cs of
                           []     -> []
                           (x:xs) -> [x] )

-- unconditionally parse a single character
item :: Parser Char
item = Parser (\cs -> case cs of
                       ""     -> []
                       (c:cs) -> [(c,cs)])



sat :: (Char -> Bool) -> Parser Char
sat p = do { c <- item; if p c then return c else mzero }

char :: Char -> Parser Char
char c = sat (c ==)

-- parse a specific string
string :: String -> Parser String
string "" = return ""
string (c:cs) = do {char c; string cs; return (c:cs)}


-- option
option :: Parser a -> Parser [a]
option p = (do x <- p
               return [x])
           +++ return []

-- zero or more repetitions
many :: Parser a -> Parser [a]
many p = many1 p +++ return []

-- one or more repetitions
many1 :: Parser a -> Parser [a]
many1 p = do {a <- p; as <- many p; return (a:as)}


-- parse a token, throwing away any leading/trailing spaces
token :: Parser a -> Parser a 
token p = do {space; a <- p; space; return a}

-- parse a string of spaces, tabs
space :: Parser String
space = many (sat (\c -> case c of
                          ' '  -> True
                          '\t' -> True
                          _    -> False))

Sleeping Barber

This is yet another classic concurrency example.

The barber has one barber chair and a waiting room with a number of chairs in it. When the barber finishes cutting a customer's hair, he dismisses the customer and then goes to the waiting room to see if there are other customers waiting. If there are, he brings one of them back to the chair and cuts his hair. If there are no other customers waiting, he returns to his chair and sleeps in it.

Each customer, when he arrives, looks to see what the barber is doing. If the barber is sleeping, then the customer wakes him up and sits in the chair. If the barber is cutting hair, then the customer goes to the waiting room. If there is a free chair in the waiting room, the customer sits in it and waits his turn. If there is no free chair, then the customer leaves.

How to represent the barber and its shop? For example, the barber could be represented as a transactional variable which has several states (cutting, sleeping). In a first instance, you could ignore waiting chairs.

import Control.Concurrent
import Control.Concurrent.STM
import Data.IORef
import Data.List


-- semaphore
type Sem = TVar Int

newSem :: Int -> IO Sem
newSem n = newTVarIO n

p :: Sem -> STM ()
p sem = do n <- readTVar sem
           if n > 0
             then writeTVar sem (n-1)
             else retry

v :: Sem -> STM ()
v sem = do n <- readTVar sem
           writeTVar sem (n+1)


testSem = do s <- newSem 5
             atomically $ p s
             atomically $ v s


-- Dining philosopher:
-- We assume that forks are unordered.
philo :: Int -> TVar Int -> Chan [Char] -> IO ()
philo no forks out = do
   atomically $ do v <- readTVar forks
                   if v <= 1 
                    then retry
                    else writeTVar forks (v-2)

   writeChan out $ "Philosopher " ++ show no ++ " is eating"
   threadDelay 1000000

   atomically $ do v <- readTVar forks
                   writeTVar forks (v+2)

   philo no forks out


printOut out = do
   txt <- readChan out
   putStrLn txt
   printOut out

testPhilo = do 
   out <- newChan
   forks <- newTVarIO 4
   forkIO $ philo 1 forks out
   forkIO $ philo 2 forks out
   forkIO $ philo 3 forks out
   printOut out
