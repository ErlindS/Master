Offen bleibt: Welcher Schritt einer Portierung wirkt wie auf welchem Gerät?

Vier Entwurfsziele: Portabilität, Offenheit, Produktivität, Kontrolle. Kokkos und RAJA verfolgen ähnliche Ziele, sind aber kein offener Industriestandard. Die Lücke in der Literatur motiviert die schrittweise Untersuchung.

Stufe 1: der erste Kernel


sycl::queue q;                                   // wählt das Gerät
float* A = sycl::malloc_shared<float>(n * n, q); // USM shared
float* B = sycl::malloc_shared<float>(n * n, q);
float* C = sycl::malloc_shared<float>(n * n, q);

q.parallel_for(sycl::range<2>{n, n}, [=](sycl::id<2> idx) {
    const std::size_t i = idx[0];
    const std::size_t j = idx[1];
    float sum = 0.0f;
    for (std::size_t k = 0; k < n; ++k)
      sum += A[i * n + k] * B[k * n + j];
    C[i * n + j] = sum;
}).wait();

Host- und Gerätecode in einer Datei (Single-Source). Im Kernel nicht erlaubt: Ausnahmen, Rekursion, virtuelle Aufrufe, dynamischer Speicher.

Kernel als Lambda, Variablen per Kopie übernommen. Der Compiler erkennt den Gerätecode und übersetzt ihn zusätzlich für die Zielgeräte. Keine eigene Kernelsprache wie bei CUDA oder OpenCL.

Host, Queue, Kernel, Work-Items

1Der Host reicht den Kernel über eine Queue ein. Jede Queue gehört zu genau einem Gerät.

2Das Gerät führt ihn als viele Work-Items aus, eines je Element von C.

3Einreichen ist asynchron: der Host arbeitet weiter, bis er wartet.

Ein Kernel beschreibt nur, was ein einzelnes Work-Item tut. Der Indexraum legt fest, wie viele es gibt. Jedes Work-Item kennt seine Position und wählt darüber seine Daten.

Speichermodell: wer kopiert wann?

USM shared (Stufe 1): ein Zeiger für Host und Gerät, die Laufzeit verschiebt automatisch – bequem, Transfer unsichtbar.

USM device (Stufe 2): Daten nur auf dem Gerät, der Host kopiert ausdrücklich – mehr Code, Transfer steuerbar.

Buffer + Accessoren (Stufe 2b): Accessor sagt lesen/schreiben, die Laufzeit leitet Kopien ab.

Grau ist bereits Bekanntes, schwarz das Neue – wie in den Abbildungen der Arbeit. Daneben gibt es USM host: Daten bleiben im Host-Speicher, das Gerät greift über den Bus zu.

Jeder Wert aus dem langsamen globalen Speicher wird einmal geladen und dann T-mal aus dem schnellen lokalen Speicher gelesen.

Jedes Work-Item lädt einen Wert der Kachel. Barriere: erst rechnen, wenn alle geladen haben. Dann rechnen alle mit den gemeinsam geladenen Werten, wieder Barriere, nächste Kachel.

  • Ohne lokalen Speicher (Stufe 3) ist SYCL gleich schnell wie CUDA – die Abstraktion kostet nichts.
  • Mit Kachelung nur zwei Drittel: in CUDA ist die Kachel schneller als Stufe 3, in SYCL langsamer → vermutlich Codeerzeugung von DPC++ für lokalen Speicher und Barrieren.
  • cuBLAS ist rund 7-mal so schnell wie der beste handgeschriebene Kernel – beide Modelle lassen gleich viel liegen.

* Stufe 1: SYCL wählt die Work-Group-Größe selbst, CUDA nutzt 16 × 16 · beide direkt nacheinander gemessen (14.11.), daher leicht andere SYCL-Werte als in den vorigen Folien · T = 64 startet in beiden Modellen nicht

Die T = 64-Grenze kommt von der Hardware (1024 Threads je Block), nicht von SYCL. Nächster Schritt wäre ein Blick in das erzeugte PTX: group_barrier gegenüber bar.sync, Adressrechnung.

Stencil: praktisch verlustfrei portiert

RTX 5060 Ti, n = 8192 (256 MB je Gitter), GB/s

Ryzen 5 5600X, GB/s

SYCLCUDA
  • Einfacher Stencil erreicht 97 % der CUDA-Bandbreite.
  • Lokaler Speicher lohnt sich nicht – weder in SYCL (−16 %) noch in CUDA (−19 %), auf der CPU halbiert er die Bandbreite. Die Caches fangen die Lesezugriffe ab.
  • 1D ist langsamer als 2D (Division und Modulo für den Index) · Warten nach jedem Schritt kostet bei n = 8192 nichts.
Ob eine Optimierung hilft, hängt vom Problem ab, nicht vom Programmiermodell. Overhead pro Kernelstart: bei n = 1024 (Kernel ca. 10 µs) sank die Bandbreite durch Warten nach jedem Schritt von 814 auf 479 GB/s. Abram et al. (ISC 2025) berichten für ihre Kernel, dass 1D schneller ist – hier das Gegenteil.

Reduktion: gleichauf – bis auf Atomics

RTX 5060 Ti, n = 226 (256 MB), GB/s

Ryzen 5 5600X, GB/s

SYCLCUDA
  • Mit Kooperation in der Work-Group erreicht SYCL 96–97 % von CUDA.
  • Bei kleinem n (224) kostet jedes Atomic je Work-Group einen festen Aufwand: nur ein Viertel der CUDA-Bandbreite. sycl::reduction umgeht das (296 GB/s).

Antworten auf F1 und F2

F1 · Konzepte

Herstellerbindung und mehrfache Codebasen löst schon Stufe 1: Single-Source und Backends. Auf einem Rechner läuft sogar dieselbe ausführbare Datei auf CPU und GPU.

Abstraktion vs. Kontrolle entschärft ein gestufter Einstieg: USM shared reicht für ein lauffähiges Programm, Transfer, Work-Groups und lokaler Speicher geben schrittweise Kontrolle zurück. Buffer gehen den umgekehrten Weg – bequem, bis zu 64 % Laufzeitkosten.

F2 · Performance-Portabilität

Funktional ist jede Stufe portabel, die Leistung nicht von selbst. SYCL vereinheitlicht die Schnittstelle, nicht die Hardware.

Kachelgröße und Optimierungswahl bleiben gerätespezifisch – auch je nach Problem. Stufe 5 macht die Bindung an Geräteparameter handhabbar.

Gegenüber nativem CUDA gleichauf ohne lokalen Speicher, beim Stencil (97 %) und bei der Reduktion (96–97 %). Abstand bei Kachelung (67 %) und Float-Atomics (Faktor 6000) – die Implementierung zählt.

Grenzen: CUDA-Vergleich und weitere Fallbeispiele nur auf RTX 5060 Ti (und Ryzen) · GPUs nur eines Herstellers · eine Implementierung · PP gilt nur für diese Gerätemenge · Host-Zeitmessung inkl. Einreichen

Specialization Constants: DPC++ emuliert sie für CUDA, AdaptiveCpp bietet sie nur über eine eigene Erweiterung. Welche Parameter variiert werden müssen, muss der Programmierer weiterhin selbst wissen. Profiling-Events würden vor allem kleine Matrizen genauer messen.
