Konzepte · Matrixmultiplikation

Stufe 1: Host, Gerät, Queue & Work-Items

12345

Single-Source: Host- und Gerätecode als C++-Lambda in einer Datei.

Queue: Verbindet Hauptprogramm mit genau einem Zielgerät.

Indexraum: Ein Work-Item berechnet jeweils ein Element C[i, j].

stufe1_usm_shared.cppMinimal-invasiver Einstieg
sycl::queue q;  // wählt Zielgerät

float* A = sycl::malloc_shared<float>(n * n, q);
float* B = sycl::malloc_shared<float>(n * n, q);
float* C = sycl::malloc_shared<float>(n * n, q);

q.parallel_for(sycl::range<2>{n, n}, [=](sycl::id<2> idx) {
  const std::size_t i = idx[0];
  const std::size_t j = idx[1];
  float sum = 0.0f;
  for (std::size_t k = 0; k < n; ++k)
    sum += A[i * n + k] * B[k * n + j];
  C[i * n + j] = sum;
}).wait();
Konzepte · Getrennte Speicher

Stufe 2: USM vs. Buffer

12345

Unified Shared Memory (USM · Zeiger)

Shared Allocation (malloc_shared): Laufzeit verschiebt Daten automatisch zwischen Host und Gerät.

Device Allocation (malloc_device): Daten liegen fest im Gerätespeicher — explizite Kopie per q.memcpy.

Buffer & Accessoren (Stufe 2b · Container)

Ein sycl::buffer kapselt Daten wie ein Container; Kernel greifen über Accessoren (read_only / write_only) darauf zu.

Transfers und Abhängigkeiten entstehen automatisch — weniger Code, aber weniger Kontrolle.

stufe2_usm_device.cpp 
// Getrennter Speicher: std::vector auf dem Host, malloc_device auf dem Gerät
float* A = sycl::malloc_device<float>(n * n, q);
float* B = sycl::malloc_device<float>(n * n, q);
float* C = sycl::malloc_device<float>(n * n, q);

q.memcpy(A, hA.data(), bytes);  q.memcpy(B, hB.data(), bytes);  q.wait();
q.parallel_for(sycl::range<2>{n, n}, [=](sycl::id<2> idx) { /* unveränderter Kernel */ }).wait();
q.memcpy(hC.data(), C, bytes).wait();
{
  sycl::buffer<float, 1> bA(hA.data(), n * n), bB(hB.data(), n * n), bC(hC.data(), n * n);
  q.submit([&](sycl::handler& h) {
    sycl::accessor A(bA, h, sycl::read_only);
    sycl::accessor B(bB, h, sycl::read_only);
    sycl::accessor C(bC, h, sycl::write_only, sycl::no_init);
    h.parallel_for(sycl::range<2>{n, n}, [=](sycl::id<2> idx) { /* Kernel */ });
  });
} // Destruktor schreibt C automatisch auf den Host zurück
Konzepte · Reihenfolge & Hierarchie

Stufe 3: Abhängigkeiten & Work-Groups

12345

Abhängigkeitsgraph (DAG)

Out-of-Order (Standard): Unabhängige Aufträge laufen parallel; Reihenfolge über sycl::event & depends_on.

In-Order-Queue: Streng sequentielle Kette — ideal für iterative Zeitschritte (z. B. 2D-Stencil).

Hierarchische Ausführung (nd_range)

stufe3_ndrange.cppEigene Work-Group-Größe W
const std::size_t np = (n + W - 1) / W * W;

q.parallel_for(
  sycl::nd_range<2>{{np, np}, {W, W}},
  [=](sycl::nd_item<2> it) {
    const auto i = it.get_global_id(0);
    const auto j = it.get_global_id(1);
    if (i >= n || j >= n) return;
    /* Berechnung C[i, j] */
  });

Das Programm wählt die Gruppengröße W × W selbst statt die Laufzeit — Voraussetzung für lokalen Speicher.

Vorteil: Jeder Wert wird pro Work-Group nur 1× aus dem langsamen globalen Speicher geladen und T-mal aus dem schnellen Local Memory wiederverwendet.

stufe4_tiling.cppCommand Group + Local Memory
q.submit([&](sycl::handler& h) {
  sycl::local_accessor<float, 2> tileA({T, T}, h);
  sycl::local_accessor<float, 2> tileB({T, T}, h);

  h.parallel_for(sycl::nd_range<2>{{np, np}, {T, T}},
    [=](sycl::nd_item<2> it) {
      auto li = it.get_local_id(0), lj = it.get_local_id(1);
      float sum = 0.0f;
      for (std::size_t t = 0; t < n; t += T) {
        tileA[li][lj] = A[i * n + t + lj];
        tileB[li][lj] = B[(t + li) * n + j];
        sycl::group_barrier(it.get_group());
        for (std::size_t k = 0; k < T; ++k)
          sum += tileA[li][k] * tileB[k][lj];
        sycl::group_barrier(it.get_group());
      }
      C[i * n + j] = sum;
    });
});

// 1) Hardwaregrenzen vor dem Kernelstart abfragen
const auto max_wg = d.get_info<info::device::max_work_group_size>();
const auto lmem   = d.get_info<info::device::local_mem_size>();

for (std::size_t t : {8, 16, 32, 64}) {
  if (t * t > max_wg || 2 * t * t * sizeof(float) > lmem)
    continue;
  // Kurzmessung → schnellstes T merken
}

// 2) Laufzeitwert als Specialization Constant übergeben

Diskussion

Beantwortung der Forschungsfragen

F1 · KONZEPTE ZUR PORTIERUNG

Gestufter Baukasten

Stufe 1 löst Herstellerbindung und mehrfache Codebasen durch Single-Source-C++ und Backends.

Stufen 2–4 lösen den Zielkonflikt Abstraktion vs. Kontrolle schrittweise: USM device, Events, nd_range und local_accessor.

Trade-off: Buffer ersparen Abhängigkeitsangaben, kosten im Aufbau jedoch bis zu 60–64 % Laufzeit/Bandbreite.

F2 · HARDWAREABHÄNGIGKEIT

Ja — Leistung bleibt geräteabhängig

Funktional portabel: Alle Programme liefen unverändert und korrekt auf allen vier Geräten.

Hardwaregrenzen: Optimale CPU-Kacheln (T = 64) starten auf GPUs nicht — Stufe 5 macht Parameter handhabbar.

Problem & Compiler: Welche Stufe lohnt, hängt vom Problemtyp und der PTX-Codeerzeugung des Backends ab.

Grenzen: 3 Kernel · GPUs eines Herstellers (AMD MI300A nicht verfügbar) · 1 Implementierung (DPC++, generisches PTX) · kein nativer CPU-OpenMP/BLAS-Vergleich.
Schluss

Fazit

01

„Einmal schreiben, überall ausführen“ gilt für die Korrektheit.

02

Die Abstimmung für hohe Leistung bleibt beim Programmierer — SYCL vereinheitlicht die Schnittstelle, nicht die Hardware.

03

Im Detail entscheiden Compiler & Backends über den Abstand zu nativem CUDA.
