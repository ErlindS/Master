Stufe 1: Aus zwei Schleifen wird ein paralleler Kernel

Stufe 12345
Single-Source: Host- und Gerätecode stehen als normales C++-Lambda in derselben Datei — keine separate Kernelsprache nötig.
Stufe 0 — Sequentielles C++1 CPU-Kern

  for (size_t j = 0; j < n; ++j) {    // äußere Schleife 2
    float sum = 0.0f;
    for (size_t k = 0; k < n; ++k) sum += A[i * n + k] * B[k * n + j];
    C[i * n + j] = sum;
  }
}

sycl::queue q; // verbindet Host mit Zielgerät
float *A = malloc_shared<float>(n*n, q); // + B, C

q.parallel_for(sycl::range<2>{n, n}, [=](sycl::id<2> idx) {
  const size_t i = idx[0], j = idx[1];
  float sum = 0.0f;
  for (size_t k = 0; k < n; ++k) sum += A[i * n + k] * B[k * n + j];
  C[i * n + j] = sum;
}).wait();

ST. 1 · USM SHARED (POINTER)

Shared Allocation

Ein gemeinsamer Pointer (malloc_shared). Laufzeit migriert Speicherseiten bei Zugriff automatisch.

✓ Minimaler Code · ✗ Transfer versteckt
ST. 2 · USM DEVICE (POINTER)

Device Allocation

Liegt fest im schnellen VRAM (malloc_device). Expliziter Transfer per q.memcpy.

✓ Volle Kontrolle & getrennt messbar!
ST. 2b · CONTAINER + ENDPUNKTE

Buffer & Accessoren

sycl::buffer kapselt Daten; Gerät greift über accessor (read_only / write_only) zu.

✓ Impliziter Graph · ✗ Laufzeit-Overhead

{

  q.submit([&](sycl::handler& h) {
    sycl::accessor A(bA, h, sycl::read_only), B(bB, h, sycl::read_only);
    sycl::accessor C(bC, h, sycl::write_only, sycl::no_init);
    h.parallel_for(sycl::range<2>{n, n}, [=](sycl::id<2> idx) { /* Kernel */ });
  });
} // Buffer-Destruktor synchronisiert und schreibt C automatisch zurück

2 · Zweistufiger Indexraum (nd_range)

stufe3_ndrange.cppEigene Gruppengröße W × W
const size_t np = (n + W - 1) / W * W;

q.parallel_for(
  sycl::nd_range<2>{{np, np}, {W, W}}, // global, lokal
  [=](sycl::nd_item<2> it) {
    const auto i = it.get_global_id(0);
    const auto j = it.get_global_id(1);
    if (i >= n || j >= n) return;
    /* Rechnung noch im globalen Speicher */
  });
Statt die Blockgröße der Laufzeit zu überlassen, teilen wir den Indexraum selbst in Work-Groups ein — isoliert messbar und Voraussetzung für Stufe 4.

Der entscheidende Vorteil: Statt dass jedes Work-Item dieselben Werte immer wieder aus dem langsamen VRAM holt, wird jeder Wert pro Gruppe nur 1× geladen und T-mal aus dem schnellen Local Memory wiederverwendet (auf der CPU: ideale L1/L2-Cache-Blöcke!).
stufe4_tiling.cppCommand Group + local_accessor + Barriere
q.submit([&](sycl::handler& h) {
  sycl::local_accessor<float, 2> tileA({T, T}, h), tileB({T, T}, h);

  h.parallel_for(sycl::nd_range<2>{{np, np}, {T, T}}, [=](sycl::nd_item<2> it) {
    float sum = 0.0f;
    for (size_t t = 0; t < n; t += T) {
      tileA[li][lj] = A[i * n + t + lj];
      tileB[li][lj] = B[(t + li) * n + j];
      sycl::group_barrier(it.get_group()); // 1. warten bis alle geladen
      for (size_t k = 0; k < T; ++k)
        sum += tileA[li][k] * tileB[k][lj];
      sycl::group_barrier(it.get_group()); // 2. warten vor Überschreiben
    }
    C[i * n + j] = sum;
  });
});

Synthese & Diskussion

Beantwortung der beiden Forschungsfragen

Antwort auf F1 · Eingesetzte Konzepte

Ein fein abgestufter Baukasten

Herstellerbindung & Code-Duplizierung löst bereits Stufe 1 (queue, Single-Source-Lambda, malloc_shared) — ein einziges Binary läuft auf CPU und GPU.

Abstraktion vs. Kontrolle wird stufenlos wählbar: von vollautomatischen Kollektiven (sycl::reduction) über explizites malloc_device & Events (depends_on) bis zu nd_range & local_accessor.

Achtung bei Buffern (2b): Nehmen Abhängigkeiten ab, kosten im Test aber bis zu 60–64 % Durchsatz bzw. Laufzeit.

Antwort auf F2 · Muss man die Hardware berücksichtigen?

Für Korrektheit nein — für hohe Leistung ja!

1. Harte Hardwaregrenzen: Optimale CPU-Parameter (T = 64) crashen auf GPUs. Stufe 5 fängt das im selben Code ab, zahlt auf CUDA aber Emulations-Overhead.

2. Problemklasse schlägt Faustregeln: Rechenproblem → Tiling; Speicherproblem → malloc_device + Gruppengröße; Reduktion → Atomics minimieren.

3. Compiler-Backend entscheidet im Detail: PTX-Codeerzeugung von DPC++ bestimmt den Abstand zu nativem CUDA.

Methodische Grenzen: 3 Kernel · GPUs eines Herstellers (AMD MI300A im Zeitraum nicht verfügbar) · 1 Compiler (DPC++ ohne gezieltes --cuda-gpu-arch) · unoptimierte CPU-Stufe-0-Baseline.
Schlusswort

Drei Erkenntnisse zum Mitnehmen

01

„Einmal schreiben, überall ausführen“ hält SYCL für die funktionale Korrektheit zu 100 Prozent ein.

02

SYCL vereinheitlicht die Schnittstelle, nicht die Physik der Hardware — Speichermodell und Gruppengrößen bleiben Entwickleraufgabe.

03

Auf den letzten Metern entscheiden Compiler-Backends und PTX-Codeerzeugung über den Abstand zu nativem CUDA.

Ausblick: Direkter Vergleich mit AdaptiveCpp · Messungen auf der AMD MI300A · gezielte Architektur-Flags (--cuda-gpu-arch).
